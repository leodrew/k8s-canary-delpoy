## Codebase Patterns

- **This is NOT a code project.** `dev/k8s` holds Kubernetes/Istio YAML, shell scripts and
  Traditional-Chinese markdown. There is no compiler, no test framework, nothing to build.
  The typecheck equivalent is `bash scripts/validate.sh` from the repo root, exit 0 = pass.
  US-001 creates that script; before it exists there is no quality gate at all.

- **Every story adds its own assertions to `scripts/validate.sh`, in the same commit as the
  change.** This is the most important rule in this run. It is what keeps the script green at
  every commit and what stops story N+3 from silently undoing story N. A story that changes a
  manifest but adds no check is not finished.

- **Tooling is thin: node / npm / npx only.** There is NO `kubectl`, NO `yq`, and NO usable
  `python` (only the Microsoft Store stub, which prints an install prompt instead of running).
  Do not try to install them and do not try to reach a cluster — there isn't one.
  YAML is parsed with the local `node_modules/.bin/js-yaml` CLI, pinned as a devDependency.
  Do not use `npx --yes js-yaml`: it needs network on every run and cannot be a quality gate.

- **Assert on parsed YAML, not on grep.** The interesting content lives inside a ConfigMap's
  `data["application.yml"]` — a YAML document embedded as a string inside another YAML
  document. Parse the outer file, then parse that string, then assert on the object.
  Grepping the raw file gives false passes on commented-out lines (there are several).

- **`canary-manual/CANARY-COMPLETE.md` is the single source of truth for the target state.**
  Read the relevant section before touching any manifest. Section 3.1 explains how config is
  loaded (and why the pod currently cannot start), section 3.5 has the complete target
  ConfigMap, and Appendix C is the required-key list with "what it falls back to if omitted".

- **Five documents under `canary-manual/` carry a "已被取代" banner** (`README.md`, `SOP.md`,
  `SOP-apply-only.md`, `canary-ops-runbook.md`). Do not follow their operational steps —
  they contain instructions that are known to cause an outage (`replicas: 0`, `rollout undo`).
  `pilot-run-guide.md` is deliberately kept: its reader is the end user, not operations.

- **YAML comments here explain WHY, at length.** Look at
  `canary-manual/track-a/release/20-deployment-stable.yaml` for the density to match. A key
  added with no comment saying what breaks without it is off-pattern for this repo.
  Prose and comments are Traditional Chinese.

- **Scope is `dev/k8s` only.** The Spring Boot backend is a separate repo at
  `dev/spring_oauth2_backend`. Never edit it. US-007 in particular only completes the k8s half
  of the probe fix — the `SecurityConfig` permitAll change it depends on is out of scope, and
  the probes keep passing unconditionally until that lands elsewhere. Say so; do not report
  the probe problem as solved.

- **Story order is load-bearing.** The ConfigMap is made complete (US-002..US-005) *before*
  the env var is flipped to replace semantics (US-006), and the file is split (US-008) *after*
  its content is correct so both copies inherit the fix. Do not reorder.

- **`scripts/validate.sh` 的擴充方式**（US-001 建立）：腳本裡有一個
  `# 之後的檢查加在這裡` 標記區段，新檢查以 `== [n] 說明 ==` 區段加在那裡、
  總結區塊之前。helper 的呼叫慣例是 `check "<名稱>" <指令> [參數...]`，指令以
  參數陣列直接執行、**不經過 eval**，所以可以原樣傳一整段帶引號的 `node -e` 斷言。
  需要 pipeline 或 shell 語法時再明確包一層 `bash -c`。

- **解析 ConfigMap 內層設定的標準寫法**（從 repo root 執行，node_modules 在 root）：
  `const y=require("js-yaml"); const cm=y.load(fs.readFileSync(f,"utf8"));`
  `const app=y.load(cm.data["application.yml"]);` —— 然後對 `app` 物件下斷言。
  js-yaml CLI 也支援多文件（`---` 分隔）的 YAML，track-b/base 底下就有幾個。

- **這台機器 `core.autocrlf=true`。** `git add` 噴的 "LF will be replaced by CRLF"
  是正常的、可以忽略；`*.sh` 已由 `.gitattributes` 釘成 LF，之後新增的腳本自動適用。
  但工作目錄裡的 `prd.json` / `progress.txt` 實際上是 LF，程式化改寫時沿用原檔行尾。

  - **`check` helper 的呼叫慣例**：`check "<名稱>" <指令> [參數...]`，指令是直接以
    參數陣列執行（`"$@"`），**不經過 eval**。所以 `check "..." node -e '...'` 可以
    原樣傳一大段帶引號的 node 斷言進去，不用煩惱 shell 二次解析。需要 pipeline 或
    shell 語法時再明確包一層 `bash -c '...'`。
  - **加新檢查的位置**：`scripts/validate.sh` 裡有一個
    `# 之後的檢查加在這裡` 的標記區段，新的 `== [n] ... ==` 區段加在那裡，
    總結區塊（ALL PASS / FAILED）之前。`CHECK_COUNT` / `FAIL_COUNT` 會自動累計。
  - **js-yaml CLI 已實測可用且行為正確**：`node_modules/.bin/js-yaml <file>` 會把
    YAML 印成 JSON、壞檔 exit 1；**支援多文件（`---` 分隔）**，track-b/base 底下
    有幾個檔案就是多文件格式，不需要另外處理。
  - **想在 node 裡解析 ConfigMap 內層設定**，走這個路徑（US-002 開始每個 story 都會用到）：
    `const y = require("js-yaml"); const cm = y.load(fs.readFileSync(f,"utf8"));`
    `const app = y.load(cm.data["application.yml"]);` 然後對 `app` 下斷言。
    從 repo root 執行時 `require("js-yaml")` 直接可解析（node_modules 在 root）。
  - **`find` 是動態的**：YAML 語法檢查用 `find canary-manual/track-a canary-manual/track-b
    -type f -name '*.yaml'`，US-008 新增的 `11-configmap-canary.yaml` 會自動被納入，
    不需要回頭改這段。注意副檔名只吃 `.yaml`（目前這兩個目錄底下沒有 `.yml`）。
  - **這台機器 `core.autocrlf=true`**：git add 時會一直噴 "LF will be replaced by CRLF"
    警告，那是正常的、可以忽略。但 shell 腳本已用 `.gitattributes` 釘成 LF，
    US-009 要新增的 `scripts/sync-config-hash.sh` 會自動套用同一條規則。
  - **`prd.json` 與 `progress.txt` 在工作目錄裡是 LF**，即使本機 `core.autocrlf=true`。
    用 node 改寫 `prd.json` 時要沿用「原檔已經在用的行尾」再寫回去，不要無條件轉成 CRLF ——
    照做的結果是 `git diff --stat` 只有 1 行變更，而不是整檔重寫的假 diff。

- **`validate.sh` 已經有共用 helper，不要重寫樣板**（US-002 建立）：
  `assert_cm_key <dotted.key.path> [期望值]` 會對 `TRACK_A_CONFIGMAPS` 陣列裡的每一份
  ConfigMap 各跑一次斷言。US-008 把 ConfigMap 拆成 -stable / -canary 之後，
  **只要把新檔名加進那個陣列**，US-002..US-005 的所有 key 檢查就會自動對兩份都跑 ——
  這正是 US-008 驗收條件說的「更新既有檢查而不是複製一份」。
  省略期望值時只檢查存在；key 沒寫 → 失敗，寫了但沒值（`null`）→ 失敗，
  空字串 `""` → 通過（`app.security.required-role` 就是刻意的空字串，US-003 會用到）。

- **檢查要比對「值」，不能只檢查 key 存在。** 這個 repo 最危險的一類錯誤不是「key 不見了」，
  而是「key 不見了之後 Spring 用自己的預設值頂上」—— 設定看起來還在，行為已經變了，
  而且錯誤訊息不會指向 ConfigMap。`redirect-uri` 是標準案例（少了 /gui_epmmFormQuery
  前綴，登入 callback 進不來）。US-004 的 `user-name-attribute: sub` 也是同一類。

- **每加一個檢查就反向測一次**：把該值改壞 → 跑 validate.sh → 確認真的 FAIL 且 exit 1 → 還原。
  一個永遠綠燈的檢查比沒有檢查更糟，因為它讓人以為有防護。改壞的方式要涵蓋
  「key 刪掉」「值改錯」「key 有但沒值」三種，它們走的是程式裡不同的分支。

- **node 是 Windows 執行檔，看不到 Git Bash 的 `/tmp`**（實測）：node 會把 `/tmp/x`
  解讀成 `C:\tmp\x`，於是 shell 寫出去的暫存檔在 node 這邊是 ENOENT。
  shell 自己的 `cp /tmp/...` 備份沒問題（那是 bash 在處理），但**只要路徑會傳進 node
  就用 repo 內的相對路徑**，用完刪掉。US-009 的 sync-config-hash.sh 會踩到這點。
  - **`node_modules/` 不進版控**，但 `scripts/validate.sh` 依賴它。腳本開頭已有 preflight：
    找不到 `node_modules/.bin/js-yaml` 就直接告訴使用者去跑 `npm install` 並 exit 1，
    而不是噴出一整排看不懂的 FAIL。
